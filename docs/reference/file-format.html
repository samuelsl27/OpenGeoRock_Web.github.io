5.4

The .ogr file format

Describes OGR Slip2D 0.1.235

An OGR Slip2D project is one plain JSON file with the extension .ogr: the geometry, the materials, the loads, the supports, every setting and, once computed, the finite-element groundwater field. It can be read, compared and kept under version control like any text file. The results of a search, which can run to thousands of surfaces with their slices, go to a separate HDF5 file. This page lists the keys of the first and the layout of the second.

5.4.1A plain JSON document#

  • Encoding. UTF-8, indented with two spaces; non-ASCII characters are written as they are, not escaped.
  • Units. Values are stored in SI (m, kN per metre of slope, kPa, kN/m³, degrees), whatever unit system the window displays: units are converted only where the interface shows or reads them.
  • Identifiers. Objects carry UUID strings, and references between them use those ids: a material points at its water surface with water_surface_id, a region assignment at its material with material_id.
  • Regions are not stored as such. The regions are computed from the external and material boundaries; what the file keeps is each assignment as a point inside a region (region_assignments), which is re-located in the recomputed regions after every geometry change.
  • The same document everywhere. The window, ogr-slip2d-cli, the operations layer and the MCP server read and write the same file; project_get returns one section of it to an agent (Section 5.1).

Saving writes the whole document, so a file saved by the current version carries every key below. A file is never modified by a calculation.

5.4.2Top-level keys#

The groundwater field is saved

Since v0.1.78 the computed seepage field is written with the mesh. Before that version a project whose materials take their pore pressure from the finite-element field reopened without it, and an analysis would have reported u=0u = 0u=0 everywhere. A model whose materials use fem pore pressures and has no field is now refused by the analysis instead (Section 5.2).

5.4.3Settings keys#

The meaning of each setting is given where it is set: Section 2.1 for the window, and catalog("settings") or settings_get for the operations layer, which list every setting with its type and options.

5.4.4Versions and compatibility#

Every file carries "format_version": "0.1", the value of FILE_FORMAT_VERSION in the program. The reader does not consult it: an older file is recognised by the keys it carries, a key that is missing takes its default, and a few conventions that changed are converted when the file is read. Those conversions are documented in the code, for example:

  • a closed boundary that repeats its first vertex at the end, as every DXF import wrote before v0.1.197, is read without the repeated vertex (the same polygon);
  • a rapid-drawdown project saved before the B̄ fields existed (v0.1.62) gets back the behaviour it was computed with;
  • a B̄ rapid-drawdown project drawn with the drawdown convention used before v0.1.69 has its water table and drawdown line exchanged, so that the model means what it meant;
  • a water pressure grid that also declares its own value type sets the groundwater method accordingly (v0.1.202).

The conversion of v0.1.69 changes, on purpose, the factor of safety of the files it applies to, and the changelog of that version says so. Nothing guarantees that an older version of the program opens a file written by a newer one.

5.4.5Results in HDF5#

The results of a search are written to an HDF5 file, normally beside the project with the same name and the extension .h5. The window writes the result of the first method after each Compute once the project has a file; ogr-slip2d-cli compute writes one file per method (Section 5.2); a script uses save_results (Section 5.3). Each file holds one search; an existing file is replaced.

Surfaces rejected before they could be sliced are counted in n_valid + n_invalid and n_attempts but have no group, so n_surfaces can be smaller than the number attempted. The file stores one search, not the model: it is read together with the .ogr it came from.

In OGR Slip2D

A surface without a factor of safety gets no fos attribute, and its reason instead, so that a reader that forgets to check gets an error naming the surface rather than a number. The module's own header still draws the metadata as a group meta and the surfaces as surface_0000; the code writes the metadata as attributes of the root and numbers the surfaces with five digits, as this page shows.
