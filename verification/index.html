How we verify OGR Slip2D

Before relying on a factor of safety, you need some evidence that the program behind it calculates correctly. We validate OGR Slip2D against published cases, closed-form solutions and analytic identities. Stored snapshots of the program's own output are not used as references, because a snapshot would preserve any bug present when it was taken.

§ 01 — The rule

What counts as a reference

Methods, solvers and formulas are all checked against results that the program did not produce. Four kinds of reference are accepted; a recording of today's output is not one of them.

01

Published cases

Factors of safety from comparative surveys, papers and reference manuals, stored with their source and a tolerance of their own.

02

Closed-form solutions

For the groundwater engine: Darcy flow, layered media and the error-function response to a step change in head.

03

Analytic identities

Results that must hold exactly. For example, active and passive support forces coincide when the target factor is 1.0.

04

Consistency

A long transient has to reproduce the steady state, and a mesh has to keep the area of its region.

If a case fails

A failing case is not edited to make it pass. The fault is either in the code or in the expected value, and the case is there to find out which. Each case carries its own tolerance, set by the quality of its source: a value read off a figure cannot be held to the precision of a tabulated one.

Why the Arai & Tagyo cases come out lower

Modern reanalyses of both Arai & Tagyo examples agree with each other and give values about 2–3 % below those published in 1985. A search in 1985 used fewer slices and fewer circles, and a finer search finds a lower minimum. The cases keep the published value, with a tolerance that covers that known gap, so they still catch a gross regression without treating the source as more precise than it is.

Method by method

Corps of Engineers #1 and #2 are checked slice by slice against the worked example in Appendix G of USACE EM 1110-2-1902, whose tables give the interslice forces and the normal forces on the slice bases. The test suite contains further checks of the methods on given surfaces.

§ 04 — The test suite

How the 5 265 tests are organised

  • There is one test file per feature area, and its header states which invariant it protects and why.
  • Each configurable setting has a test that checks it changes the result.
  • Tests restore any state they change, such as the language, the units or the caches. Otherwise unrelated tests could fail, and only when the whole suite is run.
  • The full suite runs before each release. A filtered run says so in its output and does not count as evidence for a release.
  • Continuous integration runs on Python 3.11, 3.12 and 3.13 and also checks the licence header of every file.
